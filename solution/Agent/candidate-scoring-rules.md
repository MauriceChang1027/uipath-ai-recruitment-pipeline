# 候选人评分规则

## 1. 文档目的

本文档说明候选人评估 Agent 的评分与筛选规则。当前目标岗位为：

> Software Engineer, Product (Singapore)

系统使用候选人提交的教育背景、技术技能和工作经历进行评估，输出六个维度的分数、综合分、匹配与缺失技能，以及最终筛选状态。

## 2. 基本原则

### 2.1 仅依据明确证据

所有判断必须来自候选人资料中明确提供的、与岗位相关的信息。不得根据姓名、年龄、性别、国籍、民族、宗教、婚姻状况、残障情况或其他受保护及无关特征进行判断。

学校或雇主的知名度不得作为工程能力、系统规模、技术深度、领导力或影响力的证明。只有明确描述的职责、系统、技术方案、规模和成果可以作为证据。

### 2.2 区分满足、不满足和未知

系统在内部应区分以下三种情况：

- `MET`：有明确证据证明候选人满足要求。
- `NOT_MET`：现有证据足以证明候选人不满足要求。
- `UNKNOWN`：资料不足，无法可靠判断是否满足要求。

判断优先级为：

```text
NOT_MET > UNKNOWN > MET
```

如果某项最低资格已经明确不满足，不应因为其他信息缺失而转为人工复核。缺少证据也不能直接解释为候选人不具备相应能力，应表述为“没有明确证据”。

### 2.3 最低资格与优先资格分开评估

优先资格可以提高相关维度得分，但不得单独导致候选人被淘汰。优先资格包括：

- C、C++、Java、Swift、Kotlin；
- AI 工具集成和工作流优化；
- 负责任的 AI 实践；
- Prompt Engineering、Context Engineering 和 Agent 编排；
- 持续的 AI 技能发展。

当岗位接受多种替代语言时，只要候选人明确掌握其中一种，不应把其他替代语言逐项列为缺失技能。

## 3. 最低资格要求

评估时应检查以下最低资格：

1. 至少 4 年相关编程语言的开发经验。
2. 至少 4 年大型应用开发经验，或等效的高度相关软件／产品工程经验。
3. 有成功领导重大计划、项目或团队的经验。
4. 计算机科学、计算机工程、软件工程或相关技术专业本科学历，或者具备等效的实际技术经验。
5. 掌握 Python、JavaScript、Hack 等相关脚本或编程语言。
6. 有代码评审、测试、发布、监控、可靠性改进或主动质量改进经验。
7. 能使用数据和分析理解技术问题，并提供具体的技术反馈或解决方案。

### 3.1 相关经验的计算原则

- 只计算软件工程、产品工程、应用开发、前端、后端、移动开发和相关软件系统工作。
- 不直接累计与软件工程无关的工作、商业岗位或一般数据分析岗位。
- 软件工程相关实习可以按明确时长计算，但不得自动视为高级工程、技术领导或大型系统所有权经验。
- 不得仅根据公司名称推断经历质量或系统规模。
- 如果资料明确显示相关经验少于 4 年，应判定经验要求不满足。
- 只有在任职时间或职责信息确实不足以计算相关经验时，才能设置 `ExperienceInformationInsufficient = true`。

## 4. 六维评分规则

每个维度的分数范围均为 0～100，同时必须给出：

- 支持该分数的明确证据；
- 尚未得到证明的重要信息；
- `high`、`medium` 或 `low` 置信度。

### 4.1 教育背景（10%）

| 分数范围 | 评分说明 |
|---|---|
| 90～100 | 计算机科学、计算机工程、软件工程或直接相关技术专业本科及以上学历 |
| 80～89 | 信息系统、电子电气工程、数据科学、数学、统计、物理等高度相关专业学历 |
| 65～79 | 专业不直接相关，但有明确且较强的软件工程实践经验，可视为等效技术准备 |
| 50～64 | 已知专业不相关，且等效技术经验有限 |
| 约 50 | 已知学历层级但专业缺失；保持中性评分、低置信度，不推断相关或不相关 |

大学排名和学校声誉不得影响教育得分。

### 4.2 技术能力（25%）

| 分数范围 | 评分说明 |
|---|---|
| 90～100 | 掌握多种高度相关语言，并有广泛且深入的软件工程能力证据 |
| 80～89 | 至少两种高度相关语言，并展示出较强的工程技术栈 |
| 70～79 | 至少一种主要相关语言，并掌握多项相关工程技术 |
| 60～69 | 具备相关软件开发技术栈，岗位匹配度中等 |
| 50～59 | 有一定编程能力，但缺乏明确的技术深度 |
| 0～49 | 相关技术证据非常有限 |

相关语言包括 Python、JavaScript、Hack、C、C++、Java、Swift 和 Kotlin。仅列出技能名称只能证明接触或自述熟悉，不能直接证明高级熟练度、生产经验、架构能力、扩展性能力或性能优化能力。

### 4.3 相关工程经验（30%）

| 分数范围 | 评分说明 |
|---|---|
| 90～100 | 7 年以上高度相关的软件／产品工程经验 |
| 85～89 | 6～7 年相关经验 |
| 80～84 | 5～6 年相关经验 |
| 70～79 | 4～5 年相关经验 |
| 60～69 | 3～4 年相关经验 |
| 50～59 | 2～3 年相关经验 |
| 40～49 | 1～2 年相关经验 |
| 20～39 | 明确相关经验不足 1 年 |
| 0～19 | 几乎没有相关软件工程经验 |

年限决定基础分数区间，区间内再根据岗位相关性、技术复杂度、生产责任、系统规模、明确影响和工作成果调整。

### 4.4 领导力与所有权（15%）

| 分数范围 | 评分说明 |
|---|---|
| 90～100 | 有领导重大计划、技术领导、辅导他人和端到端所有权的强证据 |
| 80～89 | 多次明确承担项目或技术领导职责 |
| 70～79 | 明确负责重要组件、项目、技术方向或重大交付 |
| 60～69 | 有一定所有权证据，但领导范围有限 |
| 50～59 | 有相关工程经验，但领导力证据不完整 |
| 40～49 | 领导力和所有权信息很少，通常应使用低置信度 |
| 0～39 | 仅在明确证据与岗位领导力要求冲突时使用 |

不得根据高级职位名称、公司声誉或工作年限自动推断领导力。

### 4.5 工程深度、扩展性与质量（15%）

| 分数范围 | 评分说明 |
|---|---|
| 90～100 | 有大型生产系统、架构、扩展性、可靠性和性能优化的强证据 |
| 80～89 | 明确具备可扩展、分布式或大型生产系统经验 |
| 70～79 | 明确展示架构、性能、扩展性、监控、可靠性或系统设计等多项能力 |
| 60～69 | 工程技术栈成熟，但大型系统证据有限 |
| 50～59 | 有一般生产软件开发经验 |
| 40～49 | 工程深度信息不足 |

### 4.6 AI 准备度（5%）

| 分数范围 | 评分说明 |
|---|---|
| 90～100 | 高级 AI 应用产生可量化效果，并具备负责任的 AI 实践 |
| 80～89 | 有较强的 AI 工程或 AI 工作流自动化经验 |
| 70～79 | 有 LLM、RAG、Agent、AI API、Prompt Engineering 或 Context Engineering 实践 |
| 60～69 | 有明确的生成式 AI 或 AI 辅助开发经验 |
| 50～59 | 有使用 Copilot、ChatGPT 等工具的基本证据 |
| 40～49 | AI 相关证据有限或缺失 |

AI 准备度属于优先资格。缺少 AI 经验不得单独导致候选人被淘汰。

## 5. 综合分计算

综合分按照以下公式计算：

```text
FinalScore =
    Education × 0.10
    + TechnicalSkills × 0.25
    + RelevantEngineeringExperience × 0.30
    + LeadershipOwnership × 0.15
    + EngineeringDepth × 0.15
    + AIReadiness × 0.05
```

计算结果四舍五入为整数。综合分用于表达候选人与岗位的整体匹配强度。

## 6. 当前代码实际生效的最终判定

当前 `main.py` 将评分门槛分为核心硬门槛和辅助审核门槛：

| 维度 | 最低分数 | 门槛类型 | 未达到时的处理 |
|---|---:|---|---|
| 技术能力 | 60 | 核心硬门槛 | 不满足岗位要求 |
| 相关工程经验 | 70 | 核心硬门槛 | 不满足岗位要求 |
| 教育背景 | 60 | 辅助审核门槛 | 人工复核 |
| 领导力与所有权 | 60 | 辅助审核门槛 | 人工复核 |

最终判定顺序为：

1. 如果 `ExperienceInformationInsufficient = true`：
   - `FitStatus = needs_review`
   - `MeetsMinimumRequirements = null`

2. 如果工作经验信息足够，但技术能力或相关工程经验未达到核心门槛：
   - `FitStatus = does_not_meet_requirements`
   - `MeetsMinimumRequirements = false`

3. 如果技术核心门槛已经达到，但教育背景或领导力未达到辅助审核门槛：
   - `FitStatus = needs_review`
   - `MeetsMinimumRequirements = null`

4. 如果全部门槛达到，并且 `FinalScore >= 75`：
   - `FitStatus = meets_requirements`
   - `MeetsMinimumRequirements = true`

5. 如果全部门槛达到，但 `FinalScore < 75`：
   - `FitStatus = needs_review`
   - `MeetsMinimumRequirements = true`

决策流程如下：

```text
工作经验信息是否足够？
├─ 否 → 人工复核
└─ 是 → 技术能力和相关经验是否达到核心门槛？
   ├─ 否 → 不满足岗位要求
   └─ 是 → 教育和领导力是否达到辅助审核门槛？
      ├─ 否 → 人工复核
      └─ 是 → 综合分是否达到 75？
         ├─ 是 → 满足岗位要求
         └─ 否 → 人工复核
```

## 7. 最终状态定义

| FitStatus | 含义 | MeetsMinimumRequirements |
|---|---|---|
| `meets_requirements` | 满足岗位要求，可以进入下一轮评估 | `true` |
| `needs_review` | 关键信息不足或整体匹配度需要人工确认 | `null` 或 `true` |
| `does_not_meet_requirements` | 现有资料已表明未达到最低门槛 | `false` |

## 8. 匹配技能与缺失技能

`MatchedSkills` 只列出候选人资料明确支持且与岗位相关的技能或能力。

`MissingSkills` 只列出：

- 岗位明确要求但候选人材料未能证明的重要技能；或
- 值得说明的重要优先资格。

不得生成包含所有未提及技术的冗长列表，也不得把可互相替代的语言当作必须同时具备的条件。

## 9. 实现一致性说明

系统提示词要求模型内部评估七项最低资格，但当前结构化模型输出不包含七项资格各自的 `MET / NOT_MET / UNKNOWN` 状态，也不包含最终 `FitStatus`。最终状态由 `main.py` 根据技术核心门槛、辅助审核门槛和 75 分综合线重新计算。

因此，当前生产运行时应以第 6 节的规则为准。如果需要完全执行七项最低资格门槛，应扩展输出模型，显式返回每项资格状态，并让最终判定直接使用这些状态。
